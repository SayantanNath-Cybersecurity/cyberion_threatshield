# PB-002: Kerberos Authentication Failure Response

## Purpose

Provide a structured analyst workflow for investigating repeated Kerberos pre-authentication failures and determining whether the activity requires escalation as potential credential-access behavior.

This playbook is based on the authentication-failure activity observed during HUNT-002 and the telemetry used for CTSHIELD-002.

## Applicable ATT&CK Context

The investigation concerns Kerberos pre-authentication failure activity.

The exact ATT&CK technique mapping should be validated against the current ATT&CK coverage matrix before assigning a final technique identifier.

## Trigger Conditions

Initiate this playbook when one or more of the following are observed:

- Multiple Windows Security Event ID `4771` events occur within a short period.
- The same source address targets multiple user accounts.
- Event ID `4771` records status `0x00000018`.
- Authentication failures are followed by successful authentication.
- Authentication failures involve privileged or sensitive accounts.
- A source generates authentication failures across multiple systems.

## Initial Triage

Record:

- Hostname
- Source IP address
- Source hostname, if available
- Target account
- Event ID
- Status code
- Pre-authentication type
- Source port
- Event timestamp
- Number of failures
- Number of distinct target accounts
- Number of affected hosts

### Relevant Windows Events

- Event ID `4771` - Kerberos pre-authentication failure
- Event ID `4624` - Successful logon
- Event ID `4625` - Failed logon
- Account management events where available

## Investigation Workflow

### Step 1: Validate the Event

Review Event ID `4771`.

Confirm:

- The event was generated by the expected Windows Security provider.
- The status value is recorded correctly.
- The target account is present.
- The source IP is present.
- The timestamp is valid.
- The pre-authentication type is available.

For the observed attack sample, the relevant status was:

`0x00000018`

### Step 2: Identify the Source

Determine:

- Which source IP generated the failure?
- Is the source address internal or external?
- Is the source host authorized to authenticate to the target?
- Is the source associated with administrative infrastructure?
- Has the source generated other authentication events?

Search for the source address across the surrounding time window.

### Step 3: Count Target Accounts

Group Event ID `4771` events by:

- Source IP
- TargetUserName
- Time window

Determine:

- Total failures
- Distinct target accounts
- Failure rate
- Time between failures

Multiple target accounts from the same source provide stronger investigative context than repeated failures against only one account.

### Step 4: Examine Authentication Outcomes

Search for successful or failed authentication following the observed failures.

Review:

- Event ID `4624`
- Event ID `4625`
- Target account
- Source address
- Authentication package
- Logon type
- Timestamp

Determine whether failed authentication activity was followed by successful access.

### Step 5: Validate Account Context

For each affected account, determine:

- Is the account active?
- Is it privileged?
- Is it a service account?
- Is the account expected to authenticate from the observed source?
- Was the account recently created or modified?
- Are there known password changes or authentication issues?

Do not classify authentication failures as malicious solely because they are repeated.

### Step 6: Determine Pattern

Assess the observed pattern.

Potential patterns include:

- Single-account authentication failure
- Repeated failures against one account
- Multiple accounts targeted from one source
- Multiple sources targeting one account
- Distributed failures across several systems
- Failures followed by successful authentication

Document the observed pattern rather than assigning an attack label without sufficient evidence.

## Evidence Collection

Preserve:

- Windows Security Event ID `4771`
- Related Event ID `4624`
- Related Event ID `4625`
- Account information
- Source host information
- Authentication timestamps
- Relevant domain-controller telemetry
- Network telemetry where available

Record the original event timestamps and data source.

## Correlation Strategy

A useful analytical model is:

`Source IP`

↓

`Multiple Event ID 4771 failures`

↓

`Different target accounts`

↓

`Authentication outcome`

For example:

`172.16.66.1`

↓

`Administrator + backdoor`

↓

`4771 + Status 0x00000018`

This pattern warrants investigation but does not independently prove password spraying.

## False-Positive Considerations

Potential legitimate causes include:

- Incorrect passwords
- Expired credentials
- Cached or stale credentials
- Misconfigured services
- Application authentication failures
- User authentication mistakes
- Service account configuration problems
- Automated applications retrying authentication

The analyst should investigate the source, accounts, frequency, and authentication outcomes before escalating.

## Escalation Criteria

Escalate when one or more of the following are observed:

- Multiple accounts targeted from the same source.
- High authentication failure frequency.
- Privileged accounts are targeted.
- Successful authentication follows repeated failures.
- The source is unauthorized or unexpected.
- Authentication activity occurs across multiple systems.
- Additional credential-access indicators are present.
- The same source is associated with other suspicious activity.

## Containment Considerations

If unauthorized credential-access activity is confirmed:

1. Identify the affected accounts.
2. Identify the source system.
3. Validate whether credentials may have been exposed.
4. Consider temporarily restricting the source according to organizational procedures.
5. Consider credential resets where compromise is established.
6. Preserve authentication and endpoint evidence.
7. Search for successful authentication following the suspicious failures.

Containment actions should account for potential impact to legitimate services and users.

## Eradication Considerations

Depending on the investigation:

- Remove unauthorized authentication tools.
- Correct compromised or misconfigured services.
- Reset compromised credentials.
- Remove unauthorized accounts if identified.
- Review scheduled tasks and services associated with the source system.
- Review additional hosts contacted by the source.
- Address configuration weaknesses that caused repeated authentication failures.

## Recovery

After containment and eradication:

1. Validate authentication from legitimate systems.
2. Confirm that suspicious failures have stopped.
3. Monitor affected accounts.
4. Review successful authentication events.
5. Confirm service accounts and applications operate normally.
6. Document recovery actions and remaining risks.

## Detection Opportunities

A stronger detection strategy should correlate:

- Event ID `4771`
- Status `0x00000018`
- Source IP
- Distinct target accounts
- Event frequency
- Time window
- Subsequent Event ID `4624`

A single Event ID `4771` should generally be treated as an authentication-failure signal rather than automatic evidence of malicious credential access.

## Detection Gap

CTSHIELD-002 currently identifies individual Event ID `4771` failures with status `0x00000018`.

HUNT-002 demonstrated that correlation across source address, target accounts, frequency, and time windows can provide additional investigative context.

A future correlation-style rule could identify repeated failures from one source against multiple accounts.

## Closure Criteria

The case may be closed when:

- The authentication failures are explained by legitimate activity, or
- Unauthorized activity has been investigated and contained, and
- Relevant authentication evidence has been preserved, and
- Any required credential remediation has been completed, and
- Detection gaps have been documented.

The closure record should include:

- Final classification
- Source system
- Affected accounts
- Authentication pattern
- Evidence reviewed
- Response actions
- Detection improvements
- Remaining uncertainty
